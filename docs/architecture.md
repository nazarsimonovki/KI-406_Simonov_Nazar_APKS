# Архітектура AI-агента (Build Engineer)

Цей документ описує архітектуру, компоненти та принципи роботи спеціалізованого AI-агента, створеного для автоматизації розробки кросплатформного C++ проєкту.

## 1. Які проблеми вирішує агент
Агент створений для автоматизації рутинних етапів розгортання та налаштування інфраструктури проєкту. Він вирішує такі проблеми:
* **Усунення ручної конфігурації:** Автоматично генерує правильну структуру каталогів, базовий код Hello World та налаштовує систему збірки CMake.
* **Стандартизація CI/CD:** Забезпечує створення правильного workflow для GitHub Actions із підтримкою матриці операційних систем, усуваючи помилки людського фактору.
* **Інтеграція тестування:** Гарантує, що проєкт одразу створюється з підключеним фреймворком для юніт-тестування GoogleTest / CTest та базовими тестами.
* **Безпека та чистота репозиторію:** Гарантує правильне налаштування `.gitignore`, щоб уникнути потрапляння бінарних файлів (каталог `build/`), кешів та секретів до системи контролю версій.

## 2. Навички, які використовує агент
Агент використовує ізольовані інструкції (skills) для виконання конкретних класів завдань. Кожен skill має визначені вхідні дані, результати та правила перевірки:
* **`project-scaffold`**: Створює мінімальний проєкт Hello World мовою C++, файл `README.md`, структуру каталогів `src/`, `tests/` та початковий `.gitignore`.
* **`build-and-test`**: Створює та налаштовує `CMakeLists.txt` для збірки проєкту, а також генерує тестову функцію та юніт-тест із використанням фреймворку тестування GoogleTest/CTest.
* **`github-actions`**: Формує файл `.github/workflows/ci.yml` із CI-матрицею (ubuntu-latest, windows-latest, macos-latest), який містить кроки для чекауту, конфігурації CMake, складання та запуску CTest.

## 3. Команди (Commands), доступні користувачу
Користувач може керувати агентом через явні іменовані команди:
* **`git-init`**: Перевіряє стан репозиторію, ініціалізує його, за потреби, та оновлює `.gitignore`.
* **`create-project`**: Викликає skill `project-scaffold` для генерації вихідного коду проєкту.
* **`create-build`**: Викликає skill `build-and-test` для генерації системи складання та тестів.
* **`create-actions`**: Викликає skill `github-actions` для створення файлу CI workflow.
* **`check`**: Виконує статичну перевірку результатів (наявність каталогів, коректність синтаксису конфігурацій, відсутність секретів та build-каталогів у Git) без внесення змін до коду.
* **`init`**: Головна оркестратор-команда. Послідовно запускає `git-init`, `create-project`, `create-build`, `create-actions` та завершує процес командою `check`.

## 4. Які дані передаються між етапами
Оскільки агент працює в контексті файлової системи, передача даних відбувається переважно через створені артефакти:
* **Від `create-project` до `create-build`**: Передається структура каталогів та інформація про мову. Ця інформація використовується для правильного написання `CMakeLists.txt`.
* **Від `create-build` до `create-actions`**: Передаються знання про команди збірки та тестування. Workflow у GitHub Actions будується на основі цих команд.
* **Від усіх етапів до `check`**: Набір згенерованих файлів та каталогів передається на фінальну перевірку валідності.

## 5. Як оркестратор обробляє помилки
Команда-оркестратор `init` координує виконання всіх етапів за суворими правилами:
1. **Послідовність та залежність:** Кожен наступний крок запускається лише після успішного завершення попереднього. (Наприклад, `create-build` не почнеться, якщо `create-project` не створив вихідні файли).
2. **Зупинка при збої:** Якщо будь-яка команда або skill завершується з помилкою, оркестратор негайно перериває ланцюжок виконання.
3. **Заборона приховування помилок:** Оркестратор не намагається "мовчки" виправити фатальні помилки або вважати роботу успішною. Він виводить повідомлення про те, на якому саме етапі стався збій, та очікує втручання користувача.
4. **Ідемпотентність:** Повторний запуск оркестратора не руйнує вже створені, правильно налаштовані файли, а лише доповнює або виправляє відсутні компоненти.

## 6. Відповідність структури файлів репозиторію
Розміщення файлів та каталогів повністю відповідає структурі, рекомендованій методичними вказівками:
```text
.
├── .github/
│   ├── agents/
│   │   └── build-engineer.agent.md   # Маніфест агента
│   ├── prompts/                      # Команди агента
│   │   ├── git-init.prompt.md
│   │   ├── create-project.prompt.md
│   │   ├── create-build.prompt.md
│   │   ├── create-actions.prompt.md
│   │   ├── check.prompt.md
│   │   └── init.prompt.md
│   ├── skills/                       # Навички агента
│   │   ├── project-scaffold/SKILL.md
│   │   ├── build-and-test/SKILL.md
│   │   └── github-actions/SKILL.md
│   └── workflows/
│       └── ci.yml                    # GitHub Actions CI workflow
├── src/                              # Вихідний код C++
│   ├── addition.hpp
│   └── main.cpp
├── tests/                            # Юніт-тести
│   └── test_main.cpp
├── docs/                             # Документація проєкту
│   ├── architecture.md
│   ├── usage.md
│   └── ai-log.md
├── CMakeLists.txt                    # Конфігурація складання CMake
├── ci.bat                            # Скрипт збірки під Windows
├── ci.sh                             # Скрипт збірки під Linux/macOS
├── README.md                         # Головний опис проєкту
└── .gitignore                        # Правила ігнорування артефактів
```
